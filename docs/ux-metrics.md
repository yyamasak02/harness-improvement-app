# ユーザー体験の指標（UX メトリクス）

目的: 「はみ出す」「遅い」「操作しづらい」を利用者の報告で初めて知るのではなく、数字で継続的に測る。
計測は**開発・CI 専用**。アプリにテレメトリ・外部送信・計測コードは入れない（`scripts/check-rules.sh` の検査 13 が機械的に強制）。

## 仕組み
- 実行: `cd frontend && npm run e2e:ux`（ビルド → Playwright で `e2e/ux-metrics.ux.ts` を実行 → 集計）。chromium が必要（初回は `npx playwright install chromium`）。
- 環境: vite のビルド結果を `vite preview` で配信し、mockApi（`window.go` が無いと自動で有効）で動かす。大量データは `window.go` の合成ブリッジ（`e2e/ux-helpers.ts`）で差し込む。実 `~/.claude`・実 `claude` は使わない。
- 結果: `frontend/ux-metrics-results/*.json`（指標ごと）と `summary.json`（集計）。gitignore 済み。CI（`ux-metrics` ジョブ）ではジョブサマリーに表を出し、アーティファクト `ux-metrics` に保存する。
- 判定: 予算（下表）を超えたら CI が失敗する。予算の定数は `frontend/e2e/ux-helpers.ts` の `budgets`（この表と一致させる）。
- 推移: アーティファクトの `summary.json` を前回と比べる。`bash scripts/ux-report.sh`（読み取り専用）が予算に対する達成率・前回比・悪化した指標を表にする。前回の結果は CI の `ux-metrics` アーティファクト（または週次 `ux-weekly` の `ux-metrics-weekly`）を `frontend/ux-metrics-previous/` に展開して置く。手順は `ux-review` skill、要約は `scripts/scout-metrics.sh`。
- 定期実行: `.github/workflows/ux-weekly.yml`（週次・permissions は contents: read のみ）が計測し、結果をアーティファクトに 90 日保存する。ワークフローから issue は投稿しない。
- 時間系は複数回の中央値で測り、予算は手元の実測の約 10 倍以上の余裕を持たせる（CI は遅く揺れるため。フレーク禁止）。予算を緩めて通さない。変える場合は `docs/decisions.md` に理由を書き、issue にする。

## 改善の優先度づけ
次の 3 点を見て、高い順に起票・着手する（迷えば p2/p3）。
1. **予算超過の大きさ**: 予算を超えた指標が最優先（p1）。超過しておらず達成率が高い（目安 70% 超）・前回比で悪化している指標がその次（p2）。健全性（はみ出し・axe 違反）は 1 件でも超過なら p1。
2. **影響する画面**: 起動・概要・セッション一覧・改善案の適用など利用頻度の高い画面や、データを書き換える操作（適用・ロールバック）に関わるものを優先する。
3. **修正の容易さ**: 小さな修正で直るものは先に直して効果を確かめる。大きな再設計が要るものは issue を分割し、`type/tech-debt` として残す。

## ラチェット（直した指標は予算を締める）
- 改善して実測が予算を大きく下回り、複数回の計測で安定したら、予算を締める（`frontend/e2e/ux-helpers.ts` の `budgets` とこの表を同時に更新）。時間系は引き続き実測の約 10 倍以上の余裕を保つ（フレーク禁止）。
- 予算を緩める場合は `docs/decisions.md` に理由を書き、issue にする（人間の確認を得る）。緩めて CI を通すことはしない。
