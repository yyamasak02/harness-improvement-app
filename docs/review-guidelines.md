# レビューガイドライン

独立したレビューエージェント（`.claude/agents/code-reviewer.md`）と人間レビュアーが従う基準。実装した本人（エージェント）のコンテキストでの自己レビューで代替しない。

## 原則
- 目的は**ハーネスを安全に改善するアプリの品質担保**。データを壊さない・秘密を漏らさない・勝手に書かない、が最優先。
- 根拠を示す。指摘は `ファイル:行` と「どの入力・状態で何が起きるか」を書く。推測だけの指摘は `minor` 以下にする。
- フォーマット・lint・型で機械的に検出されるもの（gofmt / staticcheck / tsc / ルール検査）は指摘しない。
- 範囲外の大きな改善は PR を止めず「フォローアップ候補」に書く（作者が `type/tech-debt` の issue にする）。
- 良い点も 1〜2 行書く（維持すべき設計が分かるように）。

## 観点（優先順）
1. **安全設計**（CLAUDE.md「やってはいけないこと」・`.claude/rules/safety.md`）
   - `~/.claude`・ユーザーのプロジェクトへの書き込みが applier 以外に増えていないか／許可リスト・ハッシュ照合・バックアップ・rename 手順が崩れていないか
   - digest / 対象本文 / 追加指示が masking を通っているか。ログ・エラーメッセージ・testdata に秘密や個人情報が出ないか
   - `claude -p` の許可ツールが `Read,Write` 固定・cwd がジョブディレクトリか。AI 出力が自動保存されていないか
2. **正しさ**: 境界値・空入力・エラー経路・競合（並行実行・fsnotify・キャンセル）・リソースリーク・時刻/タイムゾーン・巨大入力
3. **テスト**
   - 変更した挙動に正常系・異常系のテストがあるか。バグ修正に回帰テストがあるか
   - テストを弱めていないか（skip / 期待値の緩和 / 閾値引き下げ / sleep 頼み）。意味を失った・重複したテストが残っていないか
   - 実 `~/.claude`・実 `claude`・実時刻に依存していないか（注入されているか）
4. **クロスプラットフォーム（macOS / Windows）**: パス区切り・大文字小文字・`filepath` と `path` の使い分け・改行（CRLF）・実行ファイル名（`.exe`/`.cmd`）・シェル依存・Unix 専用 API（`syscall`）・権限ビット・ファイルロック
5. **設計・リファクタリング**: 重複、責務の混在（`app.go` にロジック）、過剰/不足な抽象化、命名、未使用コード、エラーのラップ（`%w`）。触った周辺に直すべき負債が残っていないか
6. **仕様・ドキュメント同期**: `docs/spec.md`・README・CHANGELOG・`docs/decisions.md` が挙動変更に追随しているか。UI 文言は日本語か
7. **issue との整合**: PR 本文の `Closes/Refs #N` の issue の完了条件を満たしているか。関連 issue の取りこぼし（`bash scripts/related-issues.sh` で確認）
8. **CI・スクリプト**: ワークフローの権限は最小か。外部入力をシェルに直接埋め込んでいないか。`--no-verify` 等の迂回がないか

## 重大度
| 重大度 | 意味 | 判定への影響 |
|---|---|---|
| blocker | データ破壊・秘密流出・安全設計違反・ビルド/テストが壊れる・仕様と矛盾 | REQUEST_CHANGES |
| major | 実際に起こりうる不具合、必要なテストの欠落、クロスプラットフォームでの破綻 | REQUEST_CHANGES |
| minor | 保守性・可読性・軽微な不整合（今回直すのが望ましい） | APPROVE 可（作者が対応するか issue 化） |
| nit | 好みの範囲 | APPROVE 可（書かなくてよい） |

## 判定とマーカー
- blocker / major が 1 件でもあれば `REQUEST_CHANGES`、無ければ `APPROVE`。
- レビューコメントの**最終行**に、レビューした head コミットを含むマーカーを必ず書く（`scripts/merge-pr.sh` が読む。head が進むと過去の承認は無効になる）:

```
<!-- review-agent: verdict=APPROVE sha=<head の完全な SHA> -->
```
- 再レビューでは、前回の指摘が直っているかを 1 件ずつ確認し、新しい差分だけでなく全体への影響も見る。

## コメントの形式
```
## レビュー結果: APPROVE | REQUEST_CHANGES  （head: <short sha>）
### 良い点
### 指摘
- [blocker|major|minor] `path:line` 問題 → 起きること → 提案
### フォローアップ候補（今回は対応不要）
- 候補（type/tech-debt 等）
<!-- review-agent: verdict=... sha=... -->
```

## 運用（1 MR につき独立レビュー・コミットごとに有効）
- **全てのコード変更 MR（PR）は、実装者とは別のコンテキストのレビューエージェントによるレビューを受ける。** 実装者の自己チェック（`quality-gate`）は別物で、レビューの代わりにならない。
- 承認は**レビューした head コミットに紐づく**。修正を push して head が進んだら、**新しい head に対して改めて独立レビュー**を受ける（毎回、新しいレビューエージェントを起動し、実装時の文脈は渡さず PR 番号だけ渡す）。
- マージは `bash scripts/merge-pr.sh` のみ。現在の head への `APPROVE` マーカーと CI 成功を検査する。`gh pr merge` の直接実行は権限で禁止している。
- ローカルのレビューエージェント（`review-pr` skill）と GitHub Actions の `claude-review`（ANTHROPIC_API_KEY 登録時）は同じガイドラインを使う。
- 純粋なドキュメント・ラベル・依存更新（dependabot）も、安全設計・秘密情報の観点で最低限のレビューを受ける。dependabot PR は CI 成功を確認した上で人が判断してよい。
